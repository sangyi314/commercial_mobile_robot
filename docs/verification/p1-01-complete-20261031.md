## 每阶段调用关系、原理和来源

S2：MissionRecord + Event → reduce → Decision(next,effects)。明确状态/事件身份，失败/取消先锁定业务意图；目标终态与停止分别满足才Resolve。复读YASMIN固定commit add_state合法性代码，参考分层思路后独立实现，未复制通用框架。手写时间线覆盖正常去返程、取消顺序、晚接受、错误epoch/UUID、停止时效/缺失、交接版本/超时、返程失败及一次重试预算。

S3：Runtime::call → owner Store::submit/apply → BEGIN IMMEDIATE → 准入/reduce → 状态/事件/意图/槽COMMIT → dispatch → Port。系统SQLite 3.45.1直接链接；RAII/业务规则独立实现，参考官方事务/prepare/step文档。唯一写线程与文件锁是业务所有权；SQLite锁只解决数据库写事务。真实RAISE(ABORT)、只读、busy、损坏、未知schema测试保留原DB；邮箱满/关闭明确拒绝。

S4：Python父测试 → C++Runtime子进程屏障 → 独立fsync接收文件 → SIGKILL → 重开Store。八窗口覆盖接纳提交前后、意图提交后、外部收到Send后、接受落库后、Cancel派发后、终态提交前后。每个窗口有PID、信号、退出码、恢复状态、DB快照与无重放检查，并测试另一进程被锁拒绝。未提交为ABSENT，已提交未完成为PAUSED，终态提交后为COMPLETED。不是断电或ROS协议验证。

S5：条件变量同步准入不同ID/同内容/冲突内容；随机事件从固定seed生成，SQLite独立查询活动槽/意图，独立接收端检查effect ID，逐步比较终态。保存events操作序列、trace完整状态、receiver、DB。重放需相同源码版本。随机采样不能替代已知竞态或证明全部线程调度。

S6：mission_probe通过实际Runtime/Store运行，打印synthetic标记；正常场景展示Existing/Conflict/Busy及去返程；取消场景CancelAck后PAUSED仍占槽。运行指南含新目录构建、演示、重放命令。没有复制第三方任务系统。

## 必须掌握

1. 接单何时成功？——同一事务写状态/事件/意图/槽后COMMIT成功。
2. 为什么先持久化仍不能Exactly Once？——外部发送与SQLite不原子，派发前后崩溃都可能未知。
3. CancelAck为什么不放槽？——只收到协议应答，目标或停止可能仍未决。
4. 单写者为何还要进程锁？——线程串行只约束同进程，第二所有者仍可能派发动作。
5. 8个崩溃测试能证明断电安全吗？——不能，只证明这些进程终止窗口的离线恢复政策。
